This page says what an install is made of, how it sleeps and wakes, and what keeps it awake.

## One install

One install on your account is:

- one Worker, the front door;
- one Control Durable Object (Control DO), which holds config, the message inbox, alerts and the record of every operation;
- one Runtime DO for each epoch (one image plus one Worker code version). The Runtime DO owns the container;
- one container, 2 vCPU, 6 GiB memory, 20 GB disk by default, that runs OpenClaw;
- one sandbox container for agent tools, only when `sandbox` is on;
- one R2 bucket, `oc-host-<inst>` by default.

The Worker is `oc-host` by default. Its URL is `https://<name>.<subdomain>.workers.dev`. With [Cloudflare Access](/security/#cloudflare-access) on, the URL is your custom domain.

## The owner console

The owner console is the page at your install URL (`/`). It is the same on a custom domain and on workers.dev. Without the owner cookie, it shows the login form and nothing else.

With the owner cookie, it shows a state card and three tabs. The top bar has the install name, **Open Control UI** (`/chat`) and **Sign out**. The state card shows the state (running, asleep, waking, retrying) and for how long, the last activity, the next scheduled wake, the projected month cost at the last 24 hours' pace, the check count, and one state button:

| State | Button |
|---|---|
| Asleep | **Wake now** |
| Starting | **Waking, 20 s**, disabled |
| Running | **Sleep now**. When a rule keeps the install awake, the rule shows beside the button. |
| Going to sleep | **Going to sleep**, disabled. There is no cancel. |
| Backoff, or every restore refused | **Retry now**, with the fix line of the open alert beside it |
| Stopped by you | **Start** |

Each tab is its own page. The tab names are links: Overview is `/`, Alerts and log is `/?tab=log`, and Setup is `/?tab=setup`. An item shows in one tab only. Buttons are only in Setup and Alerts and log.

| Tab | What it holds |
|---|---|
| Overview | Cost: this month at the last 24 hours' pace, the always-on month, percent saved, and the cost guard. An alerts summary that links to Alerts and log. Budgets: each daily cap with a bar, and **Raise** when one is at 80 percent. Connected checks: model (provider, model id, gateway, last test time), web search, browser and web fetch, media, each channel (transport, webhook, last platform error, whether it blocks sleep), the install (CLI, image, OpenClaw, upgrade available), config render, wake list and held inbox. Backups: newest archive age and verified flag, snapshots and chain length, replica lag, next maintenance. |
| Alerts and log | Open alerts first: severity badge, detail, fix line, and **Acknowledge** (closes the alert). For `doctor-failed`, it also shows the tail of the Doctor output. Then the log of wakes, sleeps, restarts and archives of the last 30 days, newest first, with the time and how long each took. Filter the log by kind with the links above the table. Then closed alerts. |
| Setup | Things to connect and set up, one row each with its state and one button or the command to run: Telegram, pairing requests with **Approve**, other channels, the alert channel, Access, the sandbox, the model, an upgrade or config render when one is due, and a daily limit near its cap with **Raise**. It also has **Archive now** and **Restore drill**. |

Notes:

- **Approve** does the same as `ochost pairing approve telegram <code>`. **Raise** doubles a limit, up to 1,000,000,000. A second click on the same page does not double it again.
- A status is a dot and a word: OK, Warning or Failing. A warning or failing row has the fix line that `ochost doctor` prints.
- After a button, the page returns to the tab that holds the button.
- The page follows the light or dark setting of your system.
- Opening the page does not wake the install. The model test and the Telegram webhook check run at most once a minute. While the install sleeps, those rows show the last values and say so.
- `GET /ops/doctor` serves the same JSON, and `ochost doctor` prints it. The page and the CLI agree.
- The page works with JavaScript off. Each tab is a link and each button is a form. A small script reloads the current tab every 30 seconds (5 seconds while the state changes).

## The duty cycle

The default mode is `sleep.mode: auto`. In this mode the container sleeps when it is idle and wakes when something needs it.

| Setting | Default | Meaning |
|---|---|---|
| `sleep.idleMinutes` | 5 | Idle time before sleep. It doubles after a quick re-wake, up to 60. |
| `sleep.minAwakeMinutes` | 2 | Stay awake at least this long after a boot. |
| `sleep.minSleepMinutes` | 10 | The next known wake must be at least this far away. |
| `sleep.uiIdleMinutes` | 15 | An open Control UI tab is closed after this long without user input. |
| `sleep.uiMaxMinutes` | 60 | A tab is closed after this long without a chat or a write. |
| `sleep.maxAwakeHours` | 16 | Past this uptime, the install restarts when idle. |
| `sleep.proactive` | `2h@08-22` | OpenClaw's proactive check runs every 2 hours from 08:00 to 22:00 local time. |

These keys are in `oc-host.jsonc`. Change one with `ochost config set <key> <value>`; it applies at the next op, with no deploy.

To sleep, the install also needs an empty inbox and no running turn, cron run or pending delivery. A cost guard keeps the install awake when the last 24 hours of sleep and wake cycles would cost more than always-on.

A sleep takes a snapshot of the container disk. A wake starts the container from the snapshot. Each wake gets a new generation of the SQLite replica.

## What wakes it

| Event | Wakes? |
|---|---|
| A Telegram message from a paired sender | Yes. The Worker stores and acknowledges it first. The container then starts and receives it. |
| A verified Slack (HTTP mode) or Twilio SMS event | Yes. Same path as Telegram. There is no wake list for these yet. Twilio delivery receipts do not wake. |
| A cron alarm (OpenClaw cron jobs and the proactive check) | Yes. The Control DO sets a wake alarm before the next job. |
| You open the Control UI (`/chat`) with the owner cookie | Yes. You see a waking page until the container runs. |
| You select **Wake now** in the owner console | Yes. |
| You select **Archive now** in the owner console | Yes. The archive runs in the container. |
| An `ochost` command that needs the container, such as `wake` or `backup create` | Yes. |
| Daily maintenance | Yes, if there was no wake in 24 hours or a held message is 20 hours old. |

## What does not wake it

| Event | Result |
|---|---|
| An anonymous request, a wrong path or a wrong webhook secret | 404 or 401. No wake. |
| You open the owner console at `/` | No. It shows the state and cached checks. |
| A Telegram message from an unknown sender | Stored and acknowledged. Held until the next wake. No wake. |
| A Control UI tab that was closed for idle | The tab shows "offline". Its reconnect does not wake the install. Reload the page to clear it. |

## Cold reply time

A wake is not instant. In tests:

- The first reply after a cold wake took p50 31.6 s with a mock model (30 runs).
- An acknowledged message to a running container took p50 32.9 s (200 cycles).
- One real reply came 20.8 s after the message. The model took 3.5 s of that.

While Telegram waits, the Worker shows the typing indicator and a "Waking up" message with the phase and the seconds. It deletes the message when the reply arrives. Replies stream by message edits. See [Channels](/channels/#the-waking-message). A warm-up call at boot exists but is off, because it made the first reply slower in tests.

A warm reply takes about 1 second plus model time. [Limits and tradeoffs](/limits-and-tradeoffs/) states the bound as "about a minute".

The Worker acknowledges the Telegram webhook at the edge while the container sleeps. In 200 sleep and wake cycles the acknowledgement took p50 72 ms and p99 390 ms. No update was lost.

## What keeps it awake

A channel that needs a socket keeps the install always-on. The sleep check reads the live channel status. A running channel account that does not use the managed webhook blocks sleep. Other blockers are a running cron job, an open ingress event, a pending delivery and an event-driven job. `ochost status` names the blocker. See [Channels](/channels/) and [Cost](/cost/).

## Platform reliability

A 72 hour test on Cloudflare with 24 injected faults showed 0 platform-caused container stops in 3.7 awake instance-days. The sleep-mode instance had 71 of 71 wakes succeed. After a fault we caused, the container restarted in 224 to 1045 s. The restart delay we set is 180 to 240 s of that. Restore time grew from 18 to 41 s to 215 to 249 s in the last two restarts. Cloudflare gives no uptime guarantee for containers.
